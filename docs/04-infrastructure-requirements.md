# 인프라 요구사양

## 0. 한 줄 요약

> **시장 데이터와 문서 임베딩을 상시 갱신·분석하는 시스템으로, 전용 DB 서버와
> 배치 연산 자원이 필요합니다. 최소 구성은 2 vCPU / 8 GB / 100 GB (월 약 30만원),
> 표준 구성은 8 vCPU / 32 GB / 500 GB (월 약 120만원)이며, 현재 운영
> DB(2 vCPU / 2 GB / 20 GB)와는 분리 운영이 필수입니다.**

| | 최소 권장 | 표준 권장 |
|---|---|---|
| DB | 2 vCPU / **8 GB** / 100 GB | 8 vCPU / **32 GB** / 500 GB |
| S3 | 1 TB | 3 TB |
| **월 운영비** | **약 30만원** | **약 120만원** |
| **초기 1회성** | 약 100~220만원 | 약 750~2,200만원 |
| 데이터 범위 | 2008~ · 무료 + 상용 1종 | 2000~ · 상용 전종 |

**두 구성의 차이는 사양이 아니라 데이터 범위와 저장 아키텍처입니다** (§4).
최소 구성으로 시작해 표준으로 확장하는 경로가 열려 있습니다 (§7).

> **추진 순서 (§10):** 그 앞에 **Phase 0 — 무료 데이터만으로 핵심 가설을 검증하는
> 6~8주 단계(비용 ≈ 0)** 를 둡니다. 여기서 방법론이 성립하지 않으면 **외부 데이터
> 구매 전에 중단**할 수 있습니다. 절감 수단(§5.3)을 적용하면 최소 구성 6개월
> 총 투입은 **약 220~330만원**입니다.

## 1. 왜 전용 자원이 필요한가 — 3줄 근거

| 요구 | 근거 |
|---|---|
| **스토리지 (최소 100 / 표준 500 GB)** | 문서 임베딩이 지배적. 운영 DB 실측 **청크당 20.7 KB**, 최적화 후 7 KB × 2~3천만 청크 |
| **RAM (최소 8 / 표준 32 GB)** | 벡터 인덱스를 **집계 계층에만** 거는 설계 전제. 이 설계가 없으면 200 GB+ 필요 |
| **분리 운영** | 현 운영 DB는 벡터 인덱스(466 MB)가 이미 shared_buffers(413 MB)를 초과. 여기에 얹으면 LIORA 검색 품질이 직접 저하 |

| 사용 중 | 1,567 MB (**8%**) |
| PostgreSQL | 18.3 + pgvector |
| 벡터 코퍼스 | 13,510 문서 / 60,636 청크 / 1,228 MB |
| shared_buffers | 413 MB — **HNSW 인덱스(466 MB)보다 작음** |

### 2.1 즉시 조치 — 완료 및 잔여

**✅ 완료: 스토리지 오토스케일링 활성화 (2026-07-31, 최대 100 GB).**
20 GB 고정 상태에서 디스크가 차면 DB가 쓰기 불가가 되는 리스크가 제거됐다.
비용 증가 없음(실제 사용분만 과금).

> **다만 100 GB 상한은 Phase 1 범위까지다.** 공개데이터 수집(EIA 아카이브·FERC 백필·
> NOAA)만으로도 수십 GB에 도달할 수 있으므로, **적재 진행에 맞춰 상한을 상향**하거나
> §4의 전용 인스턴스 분리 시점을 앞당겨야 한다. 상한 자체는 언제든 올릴 수 있고
> 올려두는 것만으로는 과금되지 않으므로, **여유 있게 설정하는 편이 안전하다.**

**잔여 검토:**

| 항목 | 내용 |
|---|---|
| 가용성 | Single-AZ이므로 AZ 장애 시 복구까지 서비스 중단. 운영 중요도에 따라 Multi-AZ 검토 (비용 약 2배) |
| 자격증명 | `ngip_app` 비밀번호 교체 검토. 교체 시 `.env`와 ECS 태스크 정의/시크릿을 함께 갱신 |

## 3. 규모 산정 근거

### 3.1 측정된 단위 원가

운영 DB에서 직접 측정한 값 (추정이 아님):

```
ai_document_chunks : 60,636 청크 = 1,228 MB
  → 청크당 20.7 KB   내역: 본체 11.7 · HNSW 7.9 · 전문검색 0.8 · 기타 0.3
```

### 3.2 설계 최적화 3종 → 청크당 7 KB

| 조치 | 절감 | 근거 |
|---|---|---|
| **ANN 인덱스를 집계 계층에만** | −7.9 KB | 본 시스템의 주 연산은 최근접 검색이 아니라 **날짜 구간 집계**. 유사국면 검색은 일자 단위(26년 × 365 ≈ 9,500 벡터)로 충분 |
| **halfvec (float16) 저장** | −3 KB | 벡터 정밀도 절반, 품질 손실 미미 |
| **청크 원문은 S3** | −3 KB | DB에는 벡터·메타데이터만. 원문은 추출(1회)·표시에만 필요 |

→ **20.7 KB → 약 7 KB (66% 절감)**

**첫 번째 조치가 결정적입니다.** 3천만 청크에 ANN 인덱스를 전면 적용하면 인덱스만
**237 GB**이고, 이는 동급 RAM을 요구해 인스턴스 비용이 수 배로 뜁니다.
집계 계층에만 적용하면 **75 MB**입니다.

### 3.3 데이터 규모 추정

| 구성 | 규모 | 저장 |
|---|---|---|
| 문서 청크 + 벡터 | 2,000만 ~ 3,000만 | **140 ~ 210 GB** |
| 가격·커브 (26년, 옵션 표면 포함) | 5,000만 행 | 15 ~ 25 GB |
| 파이프라인 일별 흐름 | 1,500만 행 | 5 GB |
| 기상 실측 (1961~) + 예보 추출 | 2,000만 행 | 5 ~ 10 GB |
| 수급·판별 시계열 | 수백만 행 | 2 GB |
| 산출 계층 (상태·시나리오·전망 이력) | 일별 누적 | 10 ~ 20 GB |
| WAL · 임시 · 인덱스 여유 | — | ×1.4 |
| **DB 합계** | | **250 ~ 380 GB** → **500 GB 프로비저닝** |
| **S3** (원문·NWP 추출·백업) | | **2 ~ 5 TB** |

## 4. 두 가지 구성

### 4.1 무엇이 다른가 — 사양이 아니라 **범위와 저장 구조**

| 결정 | 최소 권장 | 표준 권장 |
|---|---|---|
| **기간** | 2008-01 (18년) | 2000-01 (26년) |
| **텍스트 소스** | 무료 전종 + **상용 1종**(Platts) | 상용 전종(Platts·Argus·NGI·Reuters) + 리서치 |
| **SEC 공시** | 선별 섹션만 (MD&A·Risk Factors·8-K 본문) | 전문 |
| **청크 입도** | 큰 청크(섹션 단위) — 집계 목적에 충분 | 검색 겸용 세분 |
| **옵션 표면** | ATM IV + 25델타 스큐 | 전 스트라이크 |
| **파이프 EBB** | 핵심 10개 라인 | 20~30개 라인 |
| **기상 예보** | CPC 6–10일/8–14일 (무료) | + NWP 앙상블 추출(분산) |
| **글로벌 LNG 물동** | GIIGNL 월간 집계 | Kpler 카고 단위 |
| **청크 벡터 위치** | **S3 Parquet** (DB엔 집계만) | DB |
| 결과 청크 수 | 300~500만 | 2,000~3,000만 |
| **DB 실사용** | **약 30 GB** | 250~380 GB |

#### 최소 구성의 핵심 — 저장 아키텍처를 바꾼다

```
표준:  청크 벡터 → DB에 적재 → DB에서 날짜 구간 집계
최소:  청크 벡터 → S3 Parquet → 배치가 읽어 집계 → DB엔 집계 결과만
```

본 시스템의 주 연산이 **날짜 구간 집계**이므로, 청크 벡터를 DB에 둘 필연성이 없다.
집계는 Fargate가 S3의 Parquet을 읽어 수행하고, **DB에는 일자·엔티티 집계 벡터
(수만 개)와 정형 시계열, 산출 계층만** 둔다.

→ DB 용량이 **250~380 GB → 약 30 GB**로 내려간다. 인스턴스 등급이 두 단계 낮아진다.

**대가:** 변수 실험(§5 깔때기) 반복 시 S3 재스캔이 필요해 iteration이 느리다.
집계 방식·가중을 바꿔가며 시도하는 초기 탐색 단계에서 체감된다.

### 4.2 최소 권장 사양

| 항목 | 사양 |
|---|---|
| **DB (scen 전용)** | **db.m7g.large** — 2 vCPU / **8 GB RAM** |
| 스토리지 | **100 GB gp3** (기본 3,000 IOPS / 125 MB/s) · 오토스케일링 300 GB |
| **배치 연산** | Fargate **4 vCPU / 16 GB** (수집·임베딩·추출·집계) |
| **S3** | **1 TB** |
| 운영 DB (ngip) | 현행 유지 + 오토스케일링 활성화 |

### 4.3 표준 권장 사양

| 항목 | 사양 | 근거 |
|---|---|---|
| **DB (scen 전용)** | **db.m7g.2xlarge** — 8 vCPU / **32 GB RAM** | 버스터블(t계열) **불가** — 배치 집계는 지속 부하라 크레딧 소진 |
| 스토리지 | **500 GB gp3** · 6,000 IOPS / 500 MB/s · 오토스케일링 1 TB | 기본 IOPS·처리량으로는 대용량 스캔이 느림 |
| **배치 연산** | Fargate 4 vCPU / 16 GB (상시) | |
| **재추정 연산** | 16 vCPU / 64 GB, 주·월 임시 기동 | 상시 가동 불필요 — Fargate 또는 Spot |
| **S3** | **3 TB** | |
| (조건부) GPU | 없음 — 필요 시 임시 임차 | 임베딩은 API. 자체 파인튜닝 시에만 |

### 4.4 단계 진입 시점

두 구성 모두 **Phase 1(0~3개월, 공개데이터 수집)은 현 운영 DB로 시작 가능**하다.
전용 서버는 **상용 아카이브 적재 시점**에 필요하다.

## 5. 비용

> us-east-1 · PostgreSQL · Single-AZ · On-Demand 기준 개략치.
> 환율 1,400원 가정. **실제 발주 전 최신 요금 확인 필요.**

### 5.1 월 운영비

| 항목 | 최소 권장 | 표준 권장 |
|---|---|---|
| DB 인스턴스 | db.m7g.large ~$127 | db.m7g.2xlarge ~$506 |
| 스토리지 | 100 GB ~$12 | 500 GB + 추가 IOPS·처리량 ~$132 |
| S3 | 1 TB ~$24 | 3 TB ~$71 |
| Fargate 배치 | ~$50 | ~$150 |
| **합계 (USD)** | **~$213 / 월** | **~$859 / 월** |
| **합계 (원)** | **약 30만원 / 월** | **약 120만원 / 월** |

Reserved Instance 또는 Savings Plan 적용 시 DB 비용 **30~40% 절감** 가능
(1년 약정 기준 최소 약 20만원, 표준 약 85만원 수준).

### 5.2 초기 1회성 — 데이터 처리

| 항목 | 최소 권장 | 표준 권장 |
|---|---|---|
| 임베딩 | 400만 청크 ≈ $40 | 3,000만 청크 ≈ $300 |
| **LLM 이벤트 추출** | 필터 후 30만 문서 ≈ **$700~1,500** | 수백만 문서 ≈ **$5,000~15,000** |
| **합계 (USD)** | **$740 ~ 1,540** | **$5,300 ~ 15,300** |
| **합계 (원)** | **약 100~220만원** | **약 750~2,200만원** |

> **추출이 임베딩보다 한두 자릿수 비쌉니다.** 문서 필터링·중복 제거를 추출 앞단에
> 두는 것이 품질 설계이자 **비용 설계**입니다 (03 §5.5).

### 5.3 비용 절감 수단 **[중요]**

> **인프라는 전체 비용에서 가장 작은 항목이다.** 월 30만원을 20만원으로 깎는 것보다
> 데이터 처리비와 벤더 구매비를 다루는 것이 훨씬 크다. 절감 초점을 그쪽에 둔다.

#### 5.3.1 데이터 처리비 — 합치면 1/3 수준

| 수단 | 효과 | 적용 조건 |
|---|---|---|
| **Batch API** | **−50%** | 과거 아카이브 추출은 급하지 않다 — 배치 처리에 완벽히 부합 |
| **프롬프트 캐싱** | 입력 토큰 −30~50% | 추출 프롬프트의 고정부(스키마·엔티티 목록·지시문)가 크다 |
| **모델 등급 검증** | 최대 −90% | 구조화 필드 추출은 저가 모델로 충분할 가능성. **가정하지 말고 표본으로 검증** |
| **사건 단위 중복제거** | −60~80% | 신디케이션 배수만큼 (03 §5.5.2). 품질 설계이자 비용 설계 |
| 문서 사전 필터링 | 가변 | 관련성 없는 문서는 추출하지 않는다 |

**Batch API + 프롬프트 캐싱만으로 최소 구성 처리비가 100~220만원 → 약 40~90만원**이 된다.

#### 5.3.2 인프라

| 수단 | 효과 |
|---|---|
| **S3 Glacier Instant Retrieval** | 3 TB 월 $70 → **$12**. 추출이 끝난 원문은 콜드 데이터 |
| **Reserved Instance / Savings Plan** | DB −30~40% (1년 약정 기준) |
| Graviton(m7g/t4g) 사용 | 동급 x86 대비 −10~20% (이미 반영) |
| **최소 구성 DB 등급 재검토** | §5.3.3 |

#### 5.3.3 최소 구성 DB를 더 낮출 여지

최소 구성은 **집계를 Fargate가 S3에서 수행**하므로 DB 부하가 가볍다.
그렇다면 `db.t4g.medium`(2 vCPU / 4 GB, 월 ~$47)도 후보가 된다 — m7g.large($127) 대비 **절반 이하**.

- 버스터블이라 부하가 몰리면 크레딧 소진 위험이 있다
- **Phase 1 종료 시점의 실제 부하를 측정한 뒤 결정한다.** 사전에 확정하지 않는다
- 채택 시 최소 구성 월 운영비는 **약 30만원 → 약 19만원**

#### 5.3.4 재처리 비용 위험 — 순서로 막는다 **[원칙]**

> **추출은 1회성이 아닐 수 있다.** 초기에 `scen_event` 스키마(03 §5.4)가 바뀌면
> **전량 재추출**이며, 스키마가 3번 바뀌면 비용도 3배다.

따라서:

```
표본으로 스키마 확정 (E7)  →  그 다음에 전량 추출
```

**E7을 전량 추출 앞에 두는 것은 품질 이유만이 아니라 비용 이유이기도 하다.**
같은 논리가 임베딩에도 적용된다 — E6 판정 전에 전량 임베딩을 확정하지 않는다
(02 §9.1 게이트).

### 5.4 본 문서 범위 밖 — 별도 예산

**외부 데이터 벤더 구매비** (ICE·CME 커브 백필, Platts 아카이브, Reuters 서베이 등).
**인프라 비용을 크게 상회할 가능성이 높으며 별도 조달 검토가 필요합니다.**

특히 **ICE·CME 커브 백필은 최소 구성에서도 축소할 수 없습니다** — 현 DB의 커브
이력이 사실상 없어(03 §6.6) 시스템의 정형 변수 설계 전체가 여기에 의존합니다.
최소 구성에서는 **기간을 2008~로 줄여 비용을 낮추는 것**이 유일한 조정 수단입니다.

## 6. 최소 구성에서 잃는 것 — 정직한 정리

비용 절감의 대가를 명시합니다. **모두 나중에 복구 가능하지만, 그때 재처리 비용이 듭니다.**

| 잃는 것 | 영향 |
|---|---|
| **체제전환 표본 1개** (2000년대 수입국 국면) | Regime 전환 학습이 약해짐. "전환이란 무엇인가"의 일반화 근거가 1개 사례뿐 |
| **카트리나·리타(2005)** | Gulf Coast 재해 Signpost의 극단 표본 부족 |
| **예보 분산(dispersion)** | 기상 Signpost 한 축 상실 — 예보 불일치가 신호인 국면을 못 봄 |
| **뉴스 소스 교차검증** | 상용 1종이면 소스 편향에 노출. 동일 사건의 다각 보도로 신뢰도를 높일 수 없음 |
| **카고 단위 LNG 물동** | 글로벌 nowcast 정밀도 하락 (월간 집계로 대체) |
| **옵션 스큐 전 구간** | 컨센서스 층위 하나가 얕아짐 (§4.7 #93) |
| **변수 실험 속도** | 청크 벡터가 S3에 있어 iteration이 느림 |

## 7. 확장 경로 — 최소에서 표준으로

최소 구성은 막다른 길이 아닙니다. 순서대로 확장 가능합니다.

| 단계 | 조치 | 추가 비용 |
|---|---|---|
| 1 | 상용 뉴스 소스 추가 | 벤더비 + 재임베딩 소액 |
| 2 | 기간을 2000~로 확장 | 벤더 백필비 + 재처리 |
| 3 | 청크 벡터를 DB로 이관 (실험 속도 개선) | 인스턴스 등급 상향 |
| 4 | NWP 예보 아카이브 추가 | 처리 인력·시간 |

**아키텍처는 바뀌지 않습니다** — 계약 테이블 구조(02 §3)가 동일하므로,
확장은 데이터와 인스턴스 교체이지 재설계가 아닙니다.

**단, 원문 보존 원칙(02 §10.4)이 이 확장 경로의 전제입니다.** 원문을 S3에 온전히
보존해야 나중에 재임베딩·재추출이 가능합니다. 최소 구성에서도 **원문은 버리지
않습니다.**

## 9. 보고용 요약

**질문: "이 시스템을 하려면 어느 정도 인프라가 필요한가?"**

> 초기 3개월은 **현재 자원으로 시작 가능**하며, 본격 데이터 수집 단계부터
> 전용 DB 서버가 필요합니다. **최소 구성은 2 vCPU / 8 GB / 100 GB에 월 약 30만원,
> 표준 구성은 8 vCPU / 32 GB / 500 GB에 월 약 120만원**입니다.
> 초기 데이터 처리 1회성 비용이 각각 **약 100~220만원 / 750~2,200만원** 별도이며,
> 외부 데이터 구매비는 여기에 포함되지 않습니다.

**질문: "최소와 표준의 차이가 무엇인가?"**

> 서버 사양 차이가 아니라 **다루는 데이터의 범위 차이**입니다. 최소는 분석 기간을
> 18년(2008~), 뉴스 소스를 1종으로 줄이고, 문서 벡터를 DB 대신 S3에 두어
> DB 용량을 **380 GB → 30 GB**로 낮춘 구성입니다. 대신 2000년대 시장구조 전환
> 사례와 소스 교차검증을 포기합니다. **나중에 확장 가능하며 재설계는 필요 없습니다.**

**질문: "지금 시스템으로는 왜 안 되는가?"**

> 현재 DB는 메모리 2 GB · 디스크 20 GB로, 문서 검색 인덱스(466 MB)가 이미 메모리
> 버퍼(413 MB)를 넘어선 상태입니다. 신규 데이터는 현재의 **수십~수백 배 규모**여서,
> 같은 서버에 올리면 기존 서비스(LIORA)의 응답 속도가 직접 저하됩니다.

**질문: "단계적으로 갈 수 있는가?"**

> 가능합니다. 1단계는 공개 데이터만 다루므로 추가 자원 없이 착수하고, 상용 아카이브
> 도입 시점에 전용 서버를 구성합니다. 다만 **현재 꺼져 있는 스토리지 자동 확장은
> 지금 켜는 것을 권고**합니다 — 비용 증가 없이 현재 운영 리스크를 제거합니다.

**권고:** 최소 구성으로 착수하고, 초기 실증(E1~E6) 결과로 데이터 확장의 실익이
확인되면 표준으로 전환하는 것을 권합니다. 이 순서면 **투자가 검증을 따라갑니다.**
구체적 추진안은 §10.

### 10.0 Phase 0 — 0원 데이터 사전검증 (6~8주) **[선행]**

> **가장 비싼 결정(벤더 데이터 구매) 앞에 가장 싼 검증을 놓는다.**

무료 데이터와 **이미 보유한 자원**만으로 판정 기준의 핵심 일부를 미리 확인한다.
**비용은 사실상 0**(기존 인프라 + API 소액)이며, 여기서 걸리면 **벤더에 한 푼도 쓰기
전에** 알 수 있다.

| 판정 기준 | 0원 검증 가능성 | 방법 |
|---|---|---|
| **1. 깔때기 통과율** | **부분 가능** | 무료 텍스트(EIA TIE·NGWU·STEO·FERC·EDGAR·GDELT) + **기보유** 가격 데이터(gas_daily_prices 2020~2026)로 예비 검정 |
| **2. E6 임베딩 방향 민감도** | **완전 가능** | 구성한 문장쌍 + 기존 코퍼스 샘플. 데이터 구매와 무관 |
| **7. nowcast 정확도** | **완전 가능** | EIA 생산·저장 발표 지연 구간 vs 무료 프록시(rig count · VIIRS 플레어링 · EBB) |

**기준 1이 여기서 이미 무너지면**, 그것은 "데이터가 부족해서"가 아니라 **"접근이
성립하지 않아서"** 다 — 데이터를 더 사도 결과는 같다 (§10.3 1번 참조).

| 항목 | 내용 |
|---|---|
| 기간 | 6~8주 |
| 자원 | **현 운영 DB + 기존 Fargate** (추가 인프라 없음) |
| 비용 | **사실상 0** (LLM API 소액, 수십만원 이하) |
| 산출 | 기준 1·2·7의 예비 판정 + 임계값 설정 근거 |
| 게이트 | 통과 시 Phase 1 착수. 미통과 시 **벤더 구매 전에 재검토** |

> **부수 효과:** Phase 0에서 기준 임계값을 실제 데이터로 잡을 수 있다.
> §10.3의 "결과를 보기 전 동결"이 근거 없는 숫자가 되지 않는다.

### 10.1 제안 요지

> **① Phase 0 (6~8주, 비용 0)** — 무료 데이터로 핵심 가설 사전검증
> **② Phase 1~2 (6개월)** — 최소 구성으로 파이프라인 전체 가동
> **③ 판정** — 사전 정의한 기준으로 확대·유지·중단 결정
>
> Phase 1~2 **인프라·처리 총 투입 약 220~330만원**
> (월 19~30만원 × 6 + 처리비 40~90만원, §5.3 절감 수단 적용 기준).
> 외부 데이터 구매비 별도.

### 10.2 표현 주의 — "시나리오 하나를 검증한다"로 쓰지 않는다 **[중요]**

이 단계를 *"하나의 시나리오를 검증하는 파일럿"* 으로 기술하면, 6개월 뒤 검토 자리의
질문이 **"그 시나리오는 맞았습니까?"** 가 된다. 그것은 이 시스템이 답하기로 한 질문이
아니다 — **단일 사례의 성공은 검증이 아니라 과적합의 다른 이름**이다
(헌장 §1.1 · §7.3).

올바른 기술:

> ✗ 시나리오 하나를 골라 모델이 맞히는지 검증한다
> ✓ **파이프라인 전체를 축소 범위에서 가동하고, 사전 정의한 기준으로 확대 여부를 판정한다**

### 10.3 판정 기준 — **결과를 보기 전에 동결한다** (헌장 §7.4)

| # | 기준 | 판정이 갈리는 지점 |
|---|---|---|
| **1** | **변수 깔때기 통과율** (03 §5.8) | **최우선.** 정성 변수 중 잔차화·증분검정 통과 비율이 0에 수렴하면 헌장 §5.2의 전제 자체가 무너진 것 — **데이터를 더 사도 해결되지 않는다** |
| 2 | **E6** 임베딩 방향 민감도 | 미통과 시 좌표계 교체 → 비용·일정 재산정 필요 |
| 3 | **E1** 변수군 역할 분화 (H1) | 기각되어도 체계는 성립하나 설계 조정 |
| 4 | **E3** Regime 탐지 재현성 | 재추정마다 뒤바뀌면 운영 불가 |
| 5 | **증분 예측력** | hold-out 구간에서 STEO·선도커브 대비 개선이 있는가 (헌장 §7.2) |
| 6 | **Calibration** | 산출 분포·확률의 신뢰도와 안정성 |
| 7 | **nowcast 정확도** | 공식통계 발표 이전 추정의 정확도 — **조기에 체감 가치를 보이는 항목** |

> **1번이 핵심이다.** "데이터가 부족해서 안 된 것"과 "접근 자체가 성립하지 않는 것"을
> 구별해주는 유일한 지표다. 다른 기준이 애매해도 1번이 살아 있으면 확대 근거가 되고,
> 1번이 죽으면 확대해도 같은 결과가 나온다.

각 기준의 임계값은 착수 시점에 문서로 동결하고, 판정 후 변경하지 않는다.

### 10.4 이 단계가 **답할 수 없는 것** — 미리 밝힌다

이를 명시하지 않으면 *"6개월 했는데 시나리오가 안 나왔다"* 는 오해가 생긴다.

| 답할 수 없음 | 이유 |
|---|---|
| **체제전환 학습의 유효성** | 최소 구성은 2008~이므로 전환 표본이 1개 — 원리상 불가 (§6) |
| **Scenario 층 전체** (E7~E11) | Regime 층 이후 단계. 이 구간에 포함되지 않음 |
| 소스 교차검증의 기여 | 상용 1종만 사용 |
| 예보 분산(dispersion)의 기여 | NWP 앙상블 미포함 |

→ 확대 결정은 **§10.3의 7개 기준으로 판단하고, 위 항목은 확대 이후에 검증**한다.

### 10.5 판정은 3지선다 — 2지선다로 두지 않는다

확대/중단 두 갈래로 두면 결과가 애매할 때 관성으로 확대된다.

```
확대   →  표준 구성 전환.        기준 대부분 통과, 특히 1·5
유지   →  최소 구성으로 계속 운영. 일부만 통과했으나 산출물에 실용 가치 있음
중단   →  프로젝트 재검토.        기준 1이 바닥 — 확대해도 결과가 같음
```

**"유지"가 실질적 선택지라는 점이 중요하다.** 최소 구성은 시험대만이 아니며,
**nowcast · Regime 해석 · Outlook Ⅰ만으로도 상시 활용 가치가 있을 수 있다.**
확대하지 않는 것이 곧 실패가 아니다.

### 10.6 일정

| 구간 | 내용 | 자원 | 비용 |
|---|---|---|---|
| **Phase 0** (6~8주) | 무료 데이터로 기준 1·2·7 사전검증 | **현 운영 DB** | **≈ 0** |
| **↓ 게이트** | 미통과 시 **벤더 구매 전 재검토** | | |

| 3~5개월 | 상용 1종 적재, 임베딩·추출(스키마 확정 후), E1~E6 | 최소 구성 전용 DB | 월 19~30만 + 처리 40~90만 |
| 5~6개월 | 상태·Regime 엔진 + Outlook Ⅰ + 채점, hold-out 평가 | 동일 | 월 19~30만 |

**Phase 0을 앞에 두면 순서가 이렇게 된다:** 0원 검증 → 무료 데이터 수집 →

다만 라이브 운영 신뢰는 판정 이후에도 누적이 필요하다.

### 10.7 품의·보고용 한 문단 (인프라·추진)

> AI 기반 시장 시나리오 분석 체계 구축을 **2단계로 나누어 추진**하고자 합니다.
>
> **1단계(6~8주)는 추가 비용 없이** 무료 공개데이터와 기존 보유 자원만으로 핵심
> 가설을 검증합니다. 여기서 방법론이 성립하지 않으면 **외부 데이터 구매 전에
> 중단**할 수 있습니다.
>
> **2단계(6개월)는 최소 구성**(전용 DB 2 vCPU / 8 GB / 100 GB)으로 파이프라인
